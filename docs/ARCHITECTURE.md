# Архитектура RiskLens

Архитектурный выбор зафиксирован до реализации в рабочем чате: Go-анализатор + неизменяемые снимки, текстовый индекс, локальный ONNX worker и сохраняемый точный векторный индекс, без отдельной БД и агента.

```text
GigaCode / Qwen / skill
          │ JSON-RPC MCP stdio
          ▼
cmd/risklens-mcp → internal/mcp
          │
          ▼
internal/lens.Engine
  ├─ go/packages → AST / types → symbols / relations / source snapshot
  ├─ structural chunks → Unicode text postings
  ├─ owned Python subprocess → tokenizer + ONNX CPU → embeddings
  ├─ persistent vectors.json + content/config cache
  └─ symbol/text/vector ranks → RRF → bounded graph context
```

## Согласованность

1. Корень и лимиты проверяются, процесс удерживает системную блокировку на постоянном `server.lock`.
2. Сохраняемые Go-файлы, `go.mod`, `go.sum` читаются и хэшируются в стабильном порядке. Снимок включает конфигурацию загрузки/окружение.
3. `go/packages` получает overlay прочитанного текста и загружает текущие пакеты с тестами в offline/readonly режиме.
4. AST/типы образуют технический индекс; ошибки сохраняются в диагностике. Дубли тестовых вариантов убираются по физическому исходнику; предпочтителен дополненный внутренними тестами вариант.
5. Повторный хэш после загрузки обнаруживает конфликт. При изменениях анализ повторяется один раз, иначе публикация отклоняется.
6. Новый snapshot публикуется одной короткой критической секцией. Ответы используют один immutable snapshot. Фоновое построение векторов не блокирует навигацию.
7. Векторный worker получает подготовленные фрагменты, кэшированный content hash исключает повторный inference. Новый завершённый индекс сохраняется во временный файл, fsync, rename; дисковая запись не держит блокировку статуса.
8. Поиск использует векторы только при совпадении снимка и состоянии ready. На ошибке worker доступны exact/text. Старые позиции никогда не соединяются с новым текстом.
9. Строгие запросы проверяют содержимое до и после ответа. `batch_tools` выполняет две общие проверки. Запросы с поддержкой `freshness="snapshot"` читают готовый снимок и явно возвращают `fresh=false`; для актуальности на диске нужен строгий запрос.

Гарантия относится к наблюдаемым файлам выбранного корня. Окружение процесса фиксировано; внешние зависимости/локальные replace предполагаются подготовленными. Несохранённые буферы и внешние изменения вне корня не отслеживаются. Это оптимистическая проверка согласованности, а не файловая транзакция ОС: изменение файла сразу после последней проверки обнаружит следующий запрос.

## Идентичность и связи

Пакетные ID учитывают путь пакета, kind, получателя и имя. Поля определяются владельцем типа; объекты из импортированных вариантов пакета сводятся по позиции декларации. Для generic-функций/методов используется Origin. Локальные объявления и замыкания учитывают позицию и snapshot. Одинаковые поля локальных затенённых типов различаются.

Статические вызовы подтверждены типами. Интерфейсные реализации перечисляются только как кандидаты среди известных типов; реализации вне модуля не перечисляются. Вызовы переменной функции не разрешаются без доказательства. Вызовы вложенной функции не приписываются непосредственно внешней функции. Ограниченный SSA/VTA уточняет кандидатов и часть алиасов. Полный points-to и достижимость путей не доказываются.

Обращения к полям основаны на typed selectors и ключах структурных литералов. Контекст LHS различает прямое/составное присваивание, inc/dec, range assignment и address. Передача указателя не объявляется записью; транзитивные алиасы и порядок выполнения не восстанавливаются.

## Хранилище и поиск

Структура `vectors.json`: schema version, model_key, dimension, snapshot, `records[content_hash]` (vector, token count, windows), `chunks[chunk_id]→content_hash`. Векторный канал применяет фильтры перед вычислением similarity, остальные каналы — перед учётом ранга в RRF. Удаление старых записей — замена новым множеством живых записей. Неполный batch не публикуется. Весь технический и текстовый индекс восстанавливается при старте.

Выбран exact cosine scan вместо ANN: нет отдельного daemon, CGO или двоичного формата сторонней БД, проще переносимость и проверка. Цена — линейный поиск и больший JSON-файл. Дальнейший выбор ANN должен опираться на замеры рабочего корпуса.

Текстовый поиск использует Unicode-термы и CamelCase-компоненты, BM25 с бинарной частотой. Структурные фрагменты покрывают объявления; file-фрагменты дополняют пропуски, включая package/import и неприкреплённые комментарии. Вложенные декларации не дублируют исходник содержащей функции. Одинаковый source span не размножается из-за тестовых вариантов.

RRF использует `weight/(60+rank)`; сигнал GoDoc для пакетов имеет вес 0,5. Контекст использует индексы фрагментов по ID и символу и соседние связи в исходном порядке. Глубина, число элементов и точный размер JSON-массива контекста ограничены. Продолжение — явные ID и snapshot; это не автоматическая выгрузка всего графа.

## Выбор embeddings

E5-small выбран как компактный multilingual CPU baseline: 384 измерения, MIT, ONNX FP32. BGE-M3 даёт более длинный контекст, Qwen3-Embedding-0.6B явно поддерживает code retrieval, однако оба варианта тяжелее. Их качество на конкретной стратегии не измерялось; превосходство E5 не утверждается.

Модель, ONNX-веса, токенизатор, префиксы, pooling, окна и нормализация закреплены одним model_key. Worker проверяет manifest/hashes, загружает локальные файлы и не делает сетевых запросов. Слишком длинный input покрывается окнами с повторяемым префиксом и взвешенным средним. Число токенов и окон сохраняется, усечения нет. Максимальный вход worker — 2 MB, превышение явно диагностируется.

## Покрытие и проверка

| Возможность | Состояние |
|---|---|
| Карта пакетов, пакетный поиск, индекс соседних связей и ранняя фильтрация векторов | Реализованы, проверяются локальными тестами |
| `rule_membership` | Локальный пилот для явных возвращаемых срезов и прямого `append`; применимость в рабочем фреймворке ещё предстоит проверить |
| `required_evidence` в eval | Метрика покрытия обязательных ID в поисковой выдаче; для оценки полноты бизнес-ответа требуется отдельная разметка утверждений |
| Производственный baseline текущей сборки | Требует рабочего модуля, исходных сценариев и логов |
| Сборка правил через переменные и внешние фабрики, версии внешних параметров, сценарные доказательства | За пределами пилота |
