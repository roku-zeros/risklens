# Что запросить у коллеги после прогона

Текст для отправки исполнителю прогона. RiskLens пока не реализует все диагностические поля, перечисленные ниже: если поле недоступно, указать это, а не восстанавливать значение догадкой.

> Подготовь воспроизводимый пакет результатов прогона RiskLens. Пока не исправляй найденные проблемы и не меняй основной индекс/документ во время измерений.
>
> 1. Сохрани среду: commit/version RiskLens, версию и способ запуска GigaCode, точную команду MCP, ОС/архитектуру, CPU/RAM, Go для сборки и загрузки пакетов, конфигурацию без секретов, model key и reranker, revision исследуемого модуля, build flags, размер корпуса, `project_status`/`index_status` до и после. Отметь cold/warm cache и другие активные процессы.
> 2. Выгрузи полную последовательность MCP-вызовов в JSONL: порядковый номер/request ID, tool, arguments, start/end/duration, сырой structuredContent или error, размер ответа, snapshot. Сохрани stderr отдельно. Отметь retry и причину следующего вызова. Выдели ошибки параметров, EOF, обрезку, stale index, ожидание workers и fallback. Если лог не существовал — проведи повтор с записью, не реконструируй его из памяти.
> 3. Приложи все собственные скрипты и точные команды, особенно `drive_stats.py` и batch-драйверы. Покажи 5–10 самых дорогих цепочек: цель → запросы → ошибочные пробы → полезный результат. Посчитай время модели/клиента/драйвера отдельно от измеренного времени MCP, насколько позволяют логи. Не приписывай всю паузу Go-анализатору или embeddings.
> 4. Отдай 19 бизнес-запросов в машиночитаемом виде. Для каждого: query, продукт/процесс, expected canonical symbol IDs на указанном snapshot, допустимые альтернативы, почему результат релевантен, и неприемлемые похожие результаты. Раздели запросы, использованные для настройки, и отложенные проверочные; если все уже использовались, явно отметь это.
> 5. Выполни lexical, vector, hybrid и hybrid+reranker на одном корпусе с одинаковыми фильтрами, моделью и chunking. Для каждого запроса сохрани top-10 с позициями/оценками/каналами, ошибки, fallback, первый запуск и минимум три повтора. Отдельно покажи cold runtime, warm runtime и pair-score-cache hits. Качество и время сравнивай раздельно; недоступный режим не записывай как успешный.
> 6. Для `audit_document` сохрани документ и все страницы результата с document hash. Вручную разметь найденные сигналы: настоящая устаревшая ссылка, неоднозначное имя, слово прозы, неверная классификация инструмента. Отдельно найди реальные ошибки, которые инструмент пропустил. Приведи единицу подсчёта: уникальные ссылки/вхождения/проверки. Измерь false positives и false negatives; существование символа не считать доказательством бизнес-утверждения.
> 7. Для спорных бизнес-выводов приведи 3–5 разборов: утверждение → ожидание человека → ответ агента → точные исходные anchors → где возникла ошибка. Особенно интересны общий код, разные продукты, условная сборка наборов правил, callback/interface и перезапись поля. Раздели ошибку retrieval, отсутствующую связь графа и неправильную интерпретацию найденного кода агентом.
> 8. Сохрани `call_analysis` и примеры неизвестных целей. Сделай минимальные воспроизводимые модули для 3–5 важных пропусков/ложных связей. Если можно, сравни несколько явно заданных SSA-бюджетов с временем и peak RSS. Не называй `recovered_sites / dynamic_sites` полнотой графа.
> 9. На отдельном тестовом кэше проверь рестарт во время векторизации, второго читателя, отмену долгого запроса и переподключение после обновления. Сохрани ожидаемое и фактическое поведение, lock/errors, прогресс и оставшиеся процессы. Не удаляй lock активного основного сервера.
> 10. Сравни одну и ту же итоговую задачу в GigaCode с RiskLens и обычными инструментами на одинаковой revision, с зафиксированными prompt/model/settings. Оцени человеком правильность результата, полноту исходных доказательств, количество вызовов, wall time, input/output tokens и объём данных. Не смешивай latency retrieval с полным временем агентной задачи. Если есть возможность, повтори задачу несколько раз и сохрани все результаты.
>
> Результат: исходные JSONL/JSON и скрипты, короткий отчёт с воспроизводимыми командами, список проблем по влиянию и 3–5 минимальных fixtures. Если рабочий код нельзя передавать, сохрани исходники внутри контура, а наружу подготовь обезличенные метрики и синтетические воспроизведения с тем же поведением.

## Минимальный пакет, если времени мало

- Среда/config/status и исходный snapshot.
- Сырые запросы/ответы хотя бы для одной полной проблемной цепочки, без отбрасывания ошибок.
- 19 запросов с проверенными expected IDs и top-10 для доступных режимов.
- 10 ложных сигналов аудита, 5 реальных ошибок и примеры пропусков с ручной разметкой.
- Три минимальных примера: EOF/аргументы; динамический вызов или alias; ошибочная привязка правила к продукту.

## Форматы отдельных записей

Пример строки `calls.jsonl` (предлагаемый формат отчёта, не контракт MCP):

```json
{"sequence":1,"request_id":"1","tool":"get_source","arguments":{"file":"main.go","start_line":1,"end_line":200},"started_at":"2026-11-06T12:00:00Z","duration_ms":42,"response_bytes":128,"index_snapshot":"copy-from-response","retry_of":null,"result":null,"error":{"message":"copy actual error here"}}
```

Пример записи eval-набора:

```json
{"id":"q01","query":"Где ограничивается максимальная сумма?","scope":{"paths":["internal/product/"]},"expected_symbol_ids":["copy canonical ID from actual response"],"acceptable_alternatives":[],"relevance_explanation":"Проверено по источнику: ...","split":"held_out","index_snapshot":"copy-from-response"}
```

Пример ручной разметки аудита:

```json
{"document_hash":"copy-from-response","document_line":42,"reference":"State.Limit","tool_status":"ambiguous_symbol","human_label":"ambiguous_reference","source_claim_verified":false,"business_claim_verified":false,"note":"Нужен owner/package; несколько одноимённых полей"}
```

`held_out` ставить только если запрос не использовался при настройке. Токены брать из статистики клиента; размеры JSON и bytes не считать токенами. Недоступные значения записывать как `null` с объяснением.
